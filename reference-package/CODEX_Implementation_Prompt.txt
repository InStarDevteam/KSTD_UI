# 회사 SW 표준 정립 및 표준 적용 샘플 개발 실행 프롬프트

기준일: 2026-10-20
기준안 버전: 0.1 / 회사 승인 전 초안
현재 제공자료의 상태: 표준 조사·적용 설계. 샘플 구현 및 시험 결과는 아직 없음.

## 0. 역할과 완료 목표

당신은 회사의 소프트웨어 아키텍트, 개발 리더, UI/UX 설계자, 웹접근성 담당자, QA 담당자 역할을 수행한다.
이 저장소에서 실제 실행 가능한 샘플 SW를 구현하고, 재사용 가능한 회사 표준과 설정 파일, 표준 적용대장 Excel, 적용 결과보고서 PPTX를 완성하라. 기획서만 작성하고 종료하지 말라.

목표는 아래 연결을 실제 파일과 시험결과로 증명하는 것이다.
표준 원문/사내 규칙 ID → 적용 조건 → 화면/기능 → 구현 파일과 심볼 → 시험 ID → 실제 실행결과 → 증빙 → Excel/PPT.

실제 구현되지 않은 기능, 실행하지 않은 검사, 사용하지 못한 도구를 완료·통과·인증으로 표시하지 말라. 접근성 자동검사 통과는 웹접근성 인증이나 WCAG 전체 준수를 의미하지 않는다.

## 1. 먼저 확인할 입력과 기본 결정

함께 제공되는 파일:
1) Company_SW_Standards_Register_v0.1.xlsx
2) standards_catalog.json
3) krds_source_inventory.json, krds_section_index.json, krds_interaction_index.json
4) accessibility_scenarios.json, source_register.json
5) Company_SW_Standards_Application_Plan_v0.1.pptx
6) 첨부 원본 「디지털 정부 UI,UX 가이드라인」 수정본('25.8.).pdf
7) 첨부 원본 「디지털 서비스 UIUX 가이드라인」변경 대비표(´25.8).pdf

입력 파일이 일부 없으면 현재 폴더에서 정확한 파일명을 찾아보고, 확인되지 않은 내용을 추정하지 말고 source-gaps.json에 기록하라. 공개 공식 원문으로 보완 가능한 부분은 보완하라. 제공된 Excel은 초기 설계 자료이며 구현 증빙으로 사용할 수 없다.

기본값:
- SAMPLE_DOMAIN: 회사 브랜드 업무요청·첨부자료·처리현황 관리
- STACK_PROFILE: web-react-typescript-dotnet
- FRONTEND: React + TypeScript strict + Vite. 실행 시점의 공식 지원 안정 버전과 호환성을 확인하고 잠금파일에 고정
- BACKEND: ASP.NET Core .NET 10 LTS + C# nullable + Entity Framework Core
- DATABASE: SQLite 파일 DB를 사용하는 로컬 샘플. DB 접근을 분리해 운영 DB로 교체 가능하게 설계
- TABLE_PREFIX: fc_
- DEV_WEB_PORT: 8000
- DEV_API_PORT: 8001
- API_BASE: /api. 개발 프록시를 사용하고 배포 구조는 동일 출처를 우선 검토
- LOCALE: ko-KR. 시각·일자 표시의 시간대는 Asia/Seoul, 저장 시각은 UTC
- UI_BASELINE: 첨부 2025.08 판본. 현재 온라인 KRDS와 차이가 있으면 변경대장에 별도로 기록
- A11Y_BASELINE: KWCAG 2.2 33개 검사 항목 + WCAG 2.2 Level A 및 AA 55개 성공기준
- MDR_PROFILE: UNCONFIRMED
- DEPLOYMENT: 로컬 실행 및 재현 가능한 배포 산출물까지. 실제 외부 공개 배포는 요청 범위에 있을 때만 수행

기존 저장소에 확정된 언어·프레임워크·업무가 있으면 이를 우선 존중하고, 위 기본안과의 차이 및 표준 적용 영향을 ADR에 남겨라. 이유 없이 기술 스택을 교체하거나 다중 백엔드·마이크로서비스를 추가하지 말라.

## 2. MDR 확인과 언어별 적용 원칙

MDR의 정식 명칭, 발행기관, 버전, 대상 언어/제품이 확인되지 않았다. MISRA 또는 EU MDR로 임의 치환하지 말라.
사용자에게 정식 명칭/문서/링크를 한 번 확인하고, 답이 없으면 MDR-000을 '확인필요'로 남긴 채 나머지 구현을 진행하라. 명칭 미확정은 공통 표준 작업을 멈출 이유가 아니다. MDR 준수 완료 선언은 보류한다.

분기:
A. MISRA를 뜻한 것으로 확인되는 경우:
   - MISRA C/C++는 해당 언어의 별도 프로파일이다. C#/TypeScript 소스에 MISRA 규칙을 직접 적용했다고 표시하지 말라.
   - 원문 판본, 라이선스 접근, 분석도구 버전, 지원 규칙 목록을 확보한다. 확보하지 못한 유료 규칙 전문이나 규칙 번호를 생성하지 말라.
   - 현재 샘플에 C/C++ 코드가 없으면 해당 프로파일을 조건부 또는 해당없음으로 기록하고, 안전 코딩 원칙을 사내 웹 규칙으로 채택한 부분은 별도로 설명한다.
   - MISRA를 보여주기 위해 불필요한 C/C++ 모듈을 샘플에 끼워 넣지 말라. 별도 샘플은 사용자가 선택할 때 추가한다.
B. EU 의료기기 MDR, Regulation (EU) 2017/745인 경우:
   - 제품의 의도된 목적·의료기기 해당성·분류 확인이 먼저다. 이를 단순 코딩 스타일 표준으로 다루지 말라.
   - 정해진 제품 범위와 공식 규정, 해당되는 수명주기/위험관리/사용적합성 근거를 확보한 뒤 규제 프로파일을 별도 구성한다.
   - 현재 일반 업무요청 웹을 의료기기 적합 제품으로 주장하지 말라.
C. 사내/발주처의 다른 MDR인 경우:
   - 원문 조항을 정확히 가져와 별도 네임스페이스로 등록하고 공통규칙과 충돌을 검토한다.

## 3. 표준의 계층과 출처 관리

다음 범주를 혼합하지 말고 필드로 구분하라.
1) 법령·고시·계약상 적용 요구
2) 외부 공식 기술표준의 요구/권고
3) 해당 표준을 실무화한 회사 MUST/SHOULD 기준
4) 샘플을 위한 구체적 설계 선택

핵심 기준:
- UI/UX: 첨부 디지털 정부 UI/UX 가이드라인 2025.08 및 변경 대비표
- 국내 웹접근성: KS X OT0003, 한국형 웹 콘텐츠 접근성 지침 2.2, 2022-12-28 개정 원문
- 확장 접근성 목표: W3C WCAG 2.2 A/AA. 규범 원문과 Understanding/APG 같은 참고 구현자료를 구분
- 구현 패턴: HTML 의미구조 우선, WAI-ARIA 1.2와 APG는 커스텀 위젯에 필요한 경우 참조
- 개발보안: 행정안전부/KISA 공식 개발보안 자료의 확인된 판본, OWASP ASVS 5.0.0에서 선택한 통제 및 Cheat Sheets
- 개발 프로세스: NIST SSDF 1.1 정식판을 참고. 후속 초안은 정식 기준과 구분
- 코딩: C#/TypeScript 공식 기능과 도구 규칙, 회사가 승인한 명명·구조·예외·검증 정책

OWASP ASVS 전체 L2, MISRA 전체, ISO 인증 등의 범위를 이 목록이 모두 충족한다고 주장하지 말라. 현재 회사 통제는 선택·구체화한 기준이다. 전체 특정 등급 준수가 추가로 요구되면 해당 판본의 모든 항목을 확보하여 갭 분석을 별도로 수행한다.

출처마다 표준명, 발행기관, 판본/일자, 공식 URL 또는 원본파일, 원문 절/페이지, 수집일, 접근상태, 적용범위를 남겨라. 첨부의 인쇄 페이지와 PDF 실제 페이지를 구별한다.

주의:
- 지정 네이버 블로그 https://blog.naver.com/suresofttech/224119576754 는 사전조사에서 본문을 확보하지 못했다. 읽은 것처럼 인용하지 말라. 추가 확보되면 참고자료로 분석하고 핵심 기준은 공식 원문으로 교차 확인한다.
- 2025.8 문서에 인용된 법률명이 현재 유효하다고 자동 가정하지 말라. 2026년 디지털포용법 시행 등 현행 법령을 공식 법령정보로 재확인한다. 적용 의무는 사업/기관/계약 범위와 함께 판단한다.
- KRDS 원문 목록은 번호 항목 추출본이다. 번호 없는 스타일, 상호작용 표, 예외, 그림으로 표현된 등급을 별도로 대조한다. 추출 수를 공식 표준 총수로 표현하지 말라.
- 원문 필수/권장/우수 등급을 사내 MUST/SHOULD나 자동추출 결과로 대신하지 말라. 원문에서 확인하지 못한 등급은 '미확인'을 유지한다.

## 4. 샘플 SW의 실제 구현 범위

역할:
- 일반 사용자: 본인 요청의 등록·조회·수정 및 첨부 다운로드
- 관리자: 전체 요청 조회, 허용된 상태변경, 처리 이력 확인
- 역할 판정과 객체 단위 권한은 서버에서 강제

주요 화면과 기능:
S01 로그인/로그아웃: 실제 서버 인증, 세션 만료 안내, 비밀번호 관리자와 붙여넣기 허용
S02 홈: 상태별 건수와 업무 요약. 시각적 표현과 동등한 텍스트/표 제공
S03 요청 목록: 검색, 필터, 정렬, 페이지 이동, 결과 개수·빈 결과·오류·로딩, URL 상태 유지
S04 요청 상세: 제목·본문·상태·등록일·작성자·첨부·처리 이력, 권한별 작업
S05 단계형 등록/수정: 기본정보 → 내용·첨부 → 검토 → 완료. 뒤로 가기 시 입력 보존
S06 관리자 처리: 허용 상태전이, 변경 사유, 동시수정 방지 및 감사기록
S07 도움말/접근성 안내: 키보드 사용법, 문의 경로, 글자/모션 설정과 기본값 복원
S08 컴포넌트 갤러리: 공통 UI의 일반·초점·오류·비활성·로딩 상태, 접근 가능한 사용 예

필수 공통 상태:
- 초기 진입, 로딩, 데이터 없음, 서버 오류, 권한 없음, 세션 만료, 검증 오류, 저장 성공, 파일 초과/형식 오류
- 모달 열기·닫기·취소·확인, SPA 화면 전환, 검색결과 갱신, 업로드 진행/실패/취소

데이터:
- Users/Roles, Requests, Attachments, RequestHistories/AuditEvents 등 필요한 최소 모델
- 가상 샘플 데이터만 사용. 실제 개인/기관 데이터나 실제 정부 기관 로고를 사용하지 말라.
- 요청·첨부는 서버/DB에 실제 저장하고 재시작 후 유지한다. 업무 데이터 영속성을 localStorage 또는 Mock API로 대체하지 말라.
- 스키마 마이그레이션, seed, 개발용 reset, 백업/복원 설명을 제공한다. 기존 데이터 삭제 명령은 대상과 영향을 명시한다.
- 인증은 검증된 프레임워크 기능을 사용하고 자체 암호 알고리즘을 만들지 말라. 개발계정 초기 비밀번호는 환경변수/초기화 절차로 주입하고 운영모드 seed를 차단한다.

범위 밖 기본값:
- 결제·전자서명·의료적 판단·외부 지도·라이브 방송·동영상 콘텐츠·휴대전화 본인확인 연동
- 범위 밖 기능 관련 조항도 원장에서 삭제하지 말고 해당없음 사유와 기능 추가 시 재평가 조건을 기록한다.

## 5. 회사 코딩 및 아키텍처 규칙

다음 내용은 사내 규칙으로 명문화하고 가능한 항목을 코드 검사로 연결하라.
- 명명: TS 컴포넌트/타입 PascalCase, 변수/함수 camelCase, C# 공개 타입/멤버 PascalCase, 지역/인자 camelCase. 일관된 파일·폴더·테스트 명명
- 형식: .editorconfig, Prettier/ESLint, dotnet format. UTF-8, 개행·공백 규칙 고정
- 타입: TS strict, 경계 데이터 unknown 후 검증, no-floating-promises/no-misused-promises. 무근거 any/ts-ignore 금지
- C#: nullable enable, 분석기, IDisposable/using, CancellationToken, async I/O. .Result/.Wait 동기 대기 금지 원칙과 예외 절차
- 입력: 프런트 안내와 별개로 서버 DTO·길이·허용값·업무 제약을 검증. mass assignment 방지
- 구조: UI/애플리케이션/업무규칙/영속성의 책임 분리. 과도한 계층과 불필요한 추상화는 추가하지 않음
- 오류: 공통 ProblemDetails 또는 동등한 계약, 안정된 오류코드/추적ID, 내부 스택·비밀정보 비노출. 빈 catch 금지
- 상태: 요청 취소·타임아웃·제한된 재시도. 중복 제출·동시 수정·상태전이를 서버에서 제어
- 데이터: 파라미터 바인딩/ORM, 필요한 트랜잭션, DB 제약조건, 마이그레이션 및 실패 복구
- 시간/수치: UTC 저장과 명시적 표시 시간대, 금액 등장 시 decimal 등 적절한 자료형, 임의 문자열 날짜 계산 금지
- 문서: 공개 인터페이스의 목적·입출력·오류·제약. 설명은 코드 재서술보다 결정 이유 중심
- 복잡도: 초기 회사 경고 목표는 순환복잡도 10 초과, 중첩 3 초과. 이는 외부 표준 의무값이 아니다. 도구 산식과 제외대상을 명시하고 초과 시 분해 또는 승인된 예외
- 생성코드/외부 라이브러리/테스트코드 제외는 명시하고, 취약점·라이선스 관리는 제외하지 않음

공통 규칙과 언어 프로파일을 분리하라. Java/C/C++/Python 등 실제 코드가 없는 언어까지 준수했다고 표시하지 말라.

## 6. 보안 적용 및 검증

- SQL/명령 인젝션, 저장형/반사형 XSS, 경로 조작, 객체 단위 권한 우회를 방어
- 로그인·세션은 프레임워크 기능 사용. 쿠키의 HttpOnly/Secure/SameSite와 CSRF 토큰 정책을 구현·시험
- 관리자 API와 개별 첨부 다운로드도 서버 인가. UI 버튼 숨김만으로 권한 통제를 대체하지 않음
- HTTPS, 허용 출처, 보안 헤더/CSP를 환경과 기능에 맞게 적용. wildcard와 credentials 조합 금지
- 업로드: 크기·개수·확장자·실제 형식 검증, 랜덤 저장명, 웹루트 외 저장, 실행 금지, 다운로드 인가, 원본 파일명 안전 처리
- 업로드 보안검사/악성코드 검사 엔진이 없으면 미구현을 밝히고 위험과 운영 전 조치를 기록. 탐지엔진이 있는 것처럼 만들지 않음
- 비밀은 환경변수/secret store에 분리. 프런트 번들에는 비밀을 넣지 않음
- 감사로그는 수행자·행위·대상·시각·성공여부·추적ID를 보존하고 비밀번호·토큰·불필요한 개인정보는 제외
- 파일/CSV/Excel 내보내기 시 수식 주입을 방지하고 한글·줄바꿈·대용량 경계를 시험
- 의존성 잠금, 취약점 점검, 라이선스 목록/SBOM, 실제 사용 경로 기준의 취약점 판정과 조치기록
- 외부 URL을 받거나 서버가 URL을 가져오는 기능을 추가할 경우 SSRF 및 리다이렉트 정책 재평가

무료로 실행 가능한 기본 검사와 보유 상용 정적분석 도구를 위한 연계 포인트를 제공한다. 상용 도구를 실제 실행하지 않았으면 그 도구의 검사 실적을 표시하지 않는다.

## 7. UI/UX 기준과 2025.08 변경 반영

첨부의 디자인 원칙·스타일·컴포넌트·기본 패턴·서비스 패턴을 구조적으로 검토한다. 샘플에 등장하는 패턴은 모든 상태와 접근성 규칙까지 검토한다.

- 색상, 글꼴, 간격, 그리드, 반응형, 상태 색, 초점 스타일을 tokens 파일과 공통 컴포넌트로 관리
- 회사 자체 브랜드를 사용. 정부 공식 서비스가 아닌 샘플에 정부 공식 배너나 운영기관 식별자를 사용하지 않음
- 실제 공공 서비스로 전환하는 경우에만 권한을 갖춘 기관 자산 사용 여부를 검토. 2025.08 운영기관 표시 변경 반영(실제 본문 229~231쪽)
- 푸터 '개인정보 처리방침' 명칭 및 시각적 구분, 실제 연결된 샘플 안내 페이지 제공(실제 본문 249쪽)
- 로그인 방식을 여러 개 제공하는 경우 목록의 배치를 화면 구성에 맞게 검토(실제 본문 1007쪽의 권장). 샘플의 미연동 인증 버튼을 실제 인증처럼 표시하지 않음
- 변경 대비표의 227/246/998쪽은 해당 섹션 시작이다. 세부 수정 위치와 혼동하지 않음
- 공통 탐색, 현재 위치, 제목 위계, 본문 바로가기, 입력 도움말, 일관된 동작·버튼명
- 목록과 검색: 검색상태·결과 개수·검색어·적용필터·정렬상태·초기화·빈 결과·페이지 상태를 명확히 제공
- 입력과 오류: persistent label, 필수/선택 설명, 입력 예, 오류요약과 해당 필드 연결, 오류 후 입력 보존
- 저장 전 검토와 완료 후 후속 행동, 처리 중 중복 제출 방지 및 명확한 상태 전달
- 반응형은 화면 축소뿐 아니라 정보 우선순위·탐색·터치·표의 대안까지 설계
- 접근성 설정/고대비 모드는 기본 화면의 접근성 미비를 보완하는 우회수단으로 사용하지 않음. 모든 제공 테마를 검증

KRDS 채택 기준: 본문 최소 16px(기본 Pretendard GOV 17px), 본문 행간 150% 이상은 원문 104/106/124쪽을 기준으로 토큰에 반영한다.
선명한 화면 모드를 제공하면 원문 123쪽의 역할별 명도 대비 목표인 본문 15:1, 헤딩·레이블·아이콘 7:1, 시각적 보조정보 4.5:1을 구분하여 실측한다. 204쪽의 일반 최소 4.5:1·권장 7:1 및 WCAG AA 판정과 혼동하지 않는다.
회사 추가 목표: 주요 조작 대상 44×44 CSS px 이상, 모바일 48×48 권장. 표의 좁은 조작부 등은 별도 검토하고 '사내 추가 목표'로 표시한다.

## 8. 웹접근성과 장애유형별 사용성

KWCAG 2.2 33개와 WCAG 2.2 A/AA 55개를 독립된 표준 ID로 관리하고 연결관계만 표현한다. 두 숫자를 더해 고유 기준 개수나 전체 준수율이라고 표현하지 말라. WCAG 2.2에서 삭제된 4.1.1 Parsing은 WCAG2.2 A/AA 목록에 다시 넣지 말고, KWCAG의 마크업 오류방지는 별도 유지한다.

WCAG 준수 주장 범위를 URL·화면·사용자 역할·상태·반응형 변형으로 명시하라. 해당 범위의 전체 페이지와 업무 절차 전체가 기준을 충족해야 하며, 대표 화면 검사만으로 전체 준수를 선언하지 말라. 샘플링한 경우 검사 범위와 미검사 범위를 명시한다.

최소 구현 요구:
- HTML 의미구조, 문서 언어·제목, 랜드마크, 제목 위계, 링크/버튼의 역할·이름·상태
- 키보드만으로 모든 주요 흐름 완료. 초점 순서·표시·모달 내부 이동·닫기·원래 초점 복귀·SPA 전환 후 위치 관리
- 화면낭독기에서 입력 레이블, 설명, 필수·오류·상태 메시지가 인식되도록 연결. live region은 필요한 부분에만 사용
- 일반 텍스트 대비 4.5:1, 큰 글자 기준에 해당하는 텍스트는 3:1, 필요한 비텍스트 UI/그래픽은 3:1. 비활성·장식·로고 등 공식 예외는 원문 조건을 확인
- 200% 텍스트 확대, 320 CSS px 폭 리플로우 및 400% 확대 환경 검증. 데이터 표 등 2차원 예외는 해당 조건과 대체 수단 기록
- 문자 간격·행간 등을 사용자가 조정해도 내용/기능 손실이 없음
- 색만으로 상태를 구분하지 않고 텍스트·아이콘·패턴 제공
- WCAG 2.2 2.5.8 AA의 24×24 CSS px 또는 허용된 간격/예외 조건과, 사내 주요 대상 44×44 CSS px 이상 기준(회사 MUST 채택안), 모바일 48×48 권장 목표를 구분
- 드래그 기능에는 끌지 않고 클릭/탭만으로 수행하는 단일 포인터 대안과 키보드 대안을 각각 제공. 파일선택 버튼 등 하나의 구현이 두 요구를 충족해도 검증은 각각 수행. 복잡한 제스처의 대안, 포인터 취소, label-in-name도 확인
- 비밀번호 붙여넣기와 비밀번호 관리자 사용 허용, 불필요한 인지기억 검사 배제, 중복 정보 입력 최소화
- 시간제한은 WCAG 2.2.1의 충족 방식 또는 공식 예외를 기록. 연장 방식을 채택하면 만료 전 경고 후 최소 20초의 간단한 연장 기회와 최소 10회 연장을 제공. 제한 해제·기본값의 최소 10배 범위 조절 등 다른 방식/공식 예외는 해당 조건을 검증. 보안정책만으로 자동 예외 처리하지 않음. 인증 만료 때 민감정보를 브라우저에 무조건 영구저장하지 않음
- 자동 재생·점멸 지양, reduced-motion 반영, 동작을 멈출 수 있는 수단
- 그래프·차트는 동일 정보의 데이터 표와 설명 제공
- 미디어 도입 시 자막·대본·음성해설 등 해당 기준을 다시 활성화
- 쉬운 한국어, 모호하지 않은 버튼명, 오류의 원인과 수정방법, 되돌리기/검토 기회

대상별 수동 시험:
1) 전맹/화면낭독기: 로그인부터 요청 제출·상세·첨부 확인까지 의미와 상태 파악
2) 저시력: 확대·리플로우·고대비/forced-colors·초점 가림·텍스트 간격
3) 색각 다양성: 색 제거 상태에서 상태와 오류 구분
4) 청각장애: 음성/소리에만 의존한 알림이 없고 향후 미디어 대체 수단 확보
5) 상지/운동 제약: 키보드, 충분한 목표 크기, 드래그 대안, 시간 연장
6) 음성입력 이용자: 화면에 보이는 명칭으로 컨트롤 호출 가능
7) 인지/학습 어려움·고령자: 쉬운 문장, 단계별 진행, 입력 보존, 오류 복구, 익숙한 탐색
8) 광과민/전정 민감성: 점멸/자동 움직임 및 모션 감소
9) 일시적·상황적 제약: 한 손 조작, 모바일 화면, 느린 네트워크와 중단 복구

장애 유형만으로 사용방식을 단정하지 말고 실제 보조기술·사용자 과업으로 시험한다. 장애 당사자 참여 사용성 평가는 별도 계획과 기록을 두고, 실제 참여 없이 검증했다고 기록하지 말라.

## 9. 검증 전략과 품질 게이트

자동 검사:
- 프런트: format, lint, typecheck, 단위·컴포넌트 시험, production build
- 백엔드: restore/build, 분석기/format, 업무규칙 단위시험, 인증·인가·DB·업로드 통합시험
- E2E: Playwright 등으로 실제 로그인→등록→조회→관리처리. 키보드 흐름·오류·취소·세션 만료·권한 거부·상태 전달의 DOM 및 접근성 정보 검사 포함. 실제 화면낭독기 음성 출력과 사용 맥락은 별도 수동검사
- 접근성: axe-core 등으로 대표 화면뿐 아니라 오류, 모달, 확장영역, 완료 등 실제 상태별 검사. 도구가 검사하지 못하는 항목은 수동 목록 유지
- 보안: 의존성·비밀 탐지·정적분석. 도구 사용이 가능할 때 허가된 로컬 대상에 한해 동적 보안검사
- 보고서: JSON 스키마, ID 중복/누락, 출처/테스트/증빙 파일 존재, Excel/PPT 집계 일치

수동 검사:
- 키보드 전체 업무흐름
- Windows NVDA + Chromium 계열, 가능할 때 NVDA+Firefox
- 모바일 TalkBack+Chrome, iOS VoiceOver+Safari는 사용 가능 환경에 따라 실제 수행/미실행 분리
- 확대·리플로우·초점 가림·대비·읽기순서·텍스트 간격
- 실제 인증·입력 오류·모달·첨부의 낭독 내용과 맥락

환경이 없으면 수동 절차·예상결과·검사표를 완성하고 '미실행/환경없음'으로 남긴다. DOM snapshot, aria 검사 또는 접근성 트리 점검으로 실제 화면낭독기 검사를 통과 처리하지 말라.

제공된 접근성 시험 15개는 대표 과업 시나리오이며 전수 시험표가 아니다. 구현 범위에 적용되는 모든 KWCAG·WCAG·회사 기준에 자동 또는 수동 시험을 연결하고, 미연결 기준의 시험을 추가한다. 한 과업이 일부 측면만 확인했다면 해당 조항 전체를 통과로 처리하지 않는다.

초기 회사 품질 목표(외부 표준 수치가 아닌 회사 제안):
- 자체 작성 코드의 build/type/lint/format 오류 0
- 필수 업무·보안·회귀 시나리오 통과. 실제 실행한 시험만 집계
- 핵심 도메인/권한 모듈 line coverage 80%, branch coverage 70%를 초기 목표로 검토. 생성코드 제외와 도구 산식 명시. 수치 달성을 위한 무의미한 시험 금지
- 자동 접근성 검사 serious/critical 미해결 0을 최소 CI 차단 기준으로 하고, 낮은 심각도도 적용 표준 위반이면 해결/예외 검토. 이것만으로 AA 달성 선언 금지
- 실제 적용된 A/AA 요구의 미해결 위반이 있으면 해당 범위 준수 완료로 표시하지 않음
- 적용되는 미조치 고위험 보안취약점 0. 오탐/미사용 판단은 근거와 승인자 필요
- MDR 미확정, 수동 접근성 미실행, 운영 보안 미조치 등은 최종 잔여사항에 명시

reference_kind, source_requirement_level, company_level, applicable_languages,

requirement, planned_implementation, verification_method, priority, owner_role.

적용 기록:
rule_id, implementation_status, implementation_summary, code_refs[], test_refs[],
auto_result, manual_result, evidence_ids[], deviation_id, reviewer, reviewed_at.

증빙 기록:
evidence_id, rule_ids[], test_id, run_id, commit_sha, collected_at,
environment, browser_or_assistive_technology, tool_name, tool_version,
command, exit_code, artifact_path, sha256, result, observed, expected, limitations.

자동 생성 도구가 얻을 수 없는 reviewer·실제 화면낭독기 결과·원문 미확인 등급은 빈값/미확인으로 둔다. 코드 경로는 상대경로+심볼을 기본으로 하고 해당 commit에서의 라인 범위를 보조로 기록한다.

상태를 섞지 말라.
- 적용성: 적용 / 조건부 / 해당없음 / 확인필요
- 구현상태: 계획 / 진행 / 구현 / 예외 / 해당없음
- 검증상태: 미실행 / 통과 / 실패 / 부분확인 / 해당없음
- 원문검토상태: 확인 / 재확인필요 / 미확인

해당없음은 사유와 재평가 조건이 있어야 하며 미실행을 해당없음으로 바꾸지 않는다. 조건부/미확정은 미해결 건수로 별도 표시한다.
공식 표준에 규정된 허용 예외와 회사가 승인한 편차를 별도 필드로 관리한다. 공식 예외에는 해당 조항과 조건 충족 증빙을 요구한다. 회사 승인 편차는 외부 표준 PASS나 준수완료로 집계하지 않는다. 편차를 승인하여 배포하더라도 해당 표준의 미해결 위반과 잔여 위험은 표시한다.

집계:
- 표준별 적용 확정 건수, 조건부 건수, 해당없음 건수, 확인필요 건수
- 구현률 = 해당 표준의 적용 확정 항목 중 구현 항목 / 적용 확정 항목
- 검증완료율 = 적용 확정 항목 중 필요한 자동·수동 확인을 모두 완료한 통과 항목 / 적용 확정 항목
- 분모가 0이면 '산정대상 없음'. 0%와 구별
- 원문 항목 수, 통합 회사 통제 수, 시험 사례 수는 서로 다른 지표
- 같은 내용의 KRDS/KWCAG/WCAG 중복을 합산한 단일 인증 준수율 금지

실제 제공할 명령은 아래 작업을 수행해야 한다. 가짜 성공 스크립트나 빈 command를 만들지 말라.
- setup 또는 restore: 잠금파일로 의존성 복원 및 DB 초기화
- dev: 웹8000/API8001 실행, 포트 충돌을 명확히 안내
- verify: format/lint/type/build/unit/integration 검사
- test:e2e, test:a11y: 로컬 대상 실제 실행과 원시결과 저장

- evidence:check: ID·경로·hash·commit·시험결과의 일치와 허위 PASS 방지

CI에는 필수 자동검사, 결과 artifact 보존, 예외 만료 점검을 포함한다. CI가 실제 서비스에 연결되어 실행되지 않았다면 로컬 검증과 CI 설정 완료를 구분한다.

## 14. 단계별 실행 순서

1단계: 저장소/입력 조사, 기술스택 확인, MDR 질문 1회, 출처/버전/누락 목록 작성
2단계: 통합 기준·적용성·화면·검증 매핑, 2025.08 변경 반영, 원문 추출 후보와 비번호 규칙 대조
3단계: 공통 프로젝트 설정, 보안 기본값, tokens와 접근 가능한 공통 컴포넌트
4단계: 실제 DB/API/인증과 핵심 업무흐름을 수직으로 구현
5단계: 나머지 화면·상태·오류·권한·업로드를 구현
6단계: 자동시험 실행, 실패 수정, 수동검사 수행 또는 구체적 미실행 기록
7단계: 코드/시험/실행증빙을 원장에 연결하고 Excel/PPT/HTML 생성
8단계: 원장과 보고서 수치·파일·스크린샷·미확정 사항을 대조하여 검수

각 단계에서 결정·변경·검사·남은 위험을 CHANGE_SUMMARY.md에 기록하고 장시간 작업은 중간 결과를 저장한다. 실패 시 원인을 수정하고 영향을 받는 검증을 재수행한다. 환경 제약으로 불가능한 부분은 미완료로 표시하고, 가능한 산출물은 계속 완성한다.

## 15. 완료 정의와 최종 응답

완료 확인:
- 샘플을 새 환경에서 실행할 수 있는가?
- 실제 인증, 서버 권한, 영속 데이터, 입력·첨부·처리 흐름이 동작하는가?
- 기본 UI와 모든 주요 상태에 표준이 적용되었는가?
- 화면에 쓰인 규칙과 테스트·증빙을 동일 ID로 찾을 수 있는가?
- Excel이 실제 파일이며 상태 변경 시 집계가 바뀌는가?
- PPT가 실제 구현과 시험결과를 설명하고 계획/미검증을 분명히 표시하는가?
- MDR·원문 이상·수동 미실행·보안 운영 전 항목을 숨기지 않았는가?
- 자동검사 통과를 법적 적합성/외부 인증과 혼동하지 않았는가?

최종 응답은 한국어로 다음을 보고하라.
1) 구현된 기능과 실제 실행 방법
2) 표준별 적용/구현/검증 요약표
3) 실제 실행한 검사와 결과, 미실행 검사
4) Excel·PPT·HTML·표준문서·증빙의 실제 파일 위치
5) 미확정/미해결 항목과 다음 조치

결과를 '준수 완료'라고 표현하려면 주장한 범위의 모든 필요한 근거가 있어야 한다. 현재 환경에서 수행할 수 없는 수동 평가나 MDR 식별이 남아 있으면 그 한계를 분명히 보고하고 완료 범위를 제한하라.
